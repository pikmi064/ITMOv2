Ты правишь таблицу нагрузочных проверок в practices/practice_01/tests_load.md.

Правило отбора: нагрузочный сценарий оправдан, только если он проверяет поведение системы
именно под КОНКУРЕНЦИЕЙ за общий ресурс (пул соединений/потоков к LLM, разделяемое состояние,
таймаут, который может исчерпаться из-за очереди). Если правило синхронное, без общего состояния
между запросами (результат одного запроса не зависит от того, идут ли рядом другие запросы),
то повторение integration-теста с числом запросов >1 не даёт новой информации — это не
нагрузочный сценарий, а integration-тест, запущенный N раз.

Хороший пример (оправданный нагрузочный сценарий, уже есть в файле):
| Медленный LLM-провайдер (`REL-1`) | 10 параллельных запросов, заглушка LLM отвечает 11 секунд, 3 минуты | Все запросы завершаются контролируемым ответом за ≤ 12 с; зависших соединений и голых 500 нет | Время до ответа, код ответа, число незакрытых соединений | `REL-1`; `app/review_service.py:15` без timeout и `try/except` |
Почему оправдан: REL-1 — таймаут внешнего вызова; под конкуренцией реален риск исчерпания пула
соединений/потоков и накопления зависших запросов — это поведение, которое не видно в
одиночном integration-тесте.

Плохой пример (мнимо-нагрузочный сценарий, тоже есть в файле сейчас):
| Отказ по длине без нагрузки на LLM (`API-1`) | 20 параллельных запросов с diff 20 001 символ, 2 минуты | 100% ответов — HTTP 413; вызовов LLM = 0 | Код ответа, счётчик вызовов LLM-заглушки | `API-1`; `app/api.py:8-10` вызывает сервис без проверки длины |
Почему это плохо как нагрузочный сценарий: API-1 — синхронная проверка len(diff) без общего
состояния между запросами; результат каждого запроса не зависит от параллельности. Этот же
кейс уже покрыт integration-тестом в tests_integration.md строка 8 с одним запросом. 20
параллельных запросов не добавляют новой уверенности, только имитируют нагрузку без причины.
