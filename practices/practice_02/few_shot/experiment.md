# Few-shot

Файл ведёт OpenCode по вашим запросам. Агент записывает фактические результаты экспериментов и вносит изменения в связанные файлы. Свою оценку сообщайте ему в чате; вручную заполнять шаблон не нужно.

- Артефакт Практики 1: [`../../practice_01/tests_load.md`](../../practice_01/tests_load.md)
- Что хотим улучшить: см. формулировку в [`../prompts.md`](../prompts.md) — в таблице нет критерия, какой нагрузочный сценарий оправдан (проверяет поведение именно под конкуренцией за общий ресурс между параллельными запросами), а какой лишь повторяет integration-тест с числом запросов >1. Из-за отсутствия критерия 2 из 4 сценариев (`API-1`) дублировали `tests_integration.md`.

## Примеры

### Хороший результат

Оправданный нагрузочный сценарий (уже был в файле):

```
| Медленный LLM-провайдер (`REL-1`) | 10 параллельных запросов, заглушка LLM отвечает 11 секунд, 3 минуты | Все запросы завершаются контролируемым ответом за ≤ 12 с; зависших соединений и голых 500 нет | Время до ответа, код ответа, число незакрытых соединений | `REL-1`; `app/review_service.py:15` без timeout и `try/except` |
```

Почему хороший: `REL-1` — таймаут внешнего вызова; под конкуренцией реален риск исчерпания пула соединений/потоков и накопления зависших запросов — поведение, невидимое в одиночном integration-тесте. Риск подтверждён кодом, уже существующим в diff (`app/review_service.py:15`).

### Плохой результат

Мнимо-нагрузочный сценарий (тоже был в файле до правки):

```
| Отказ по длине без нагрузки на LLM (`API-1`) | 20 параллельных запросов с diff 20 001 символ, 2 минуты | 100% ответов — HTTP 413; вызовов LLM = 0 | Код ответа, счётчик вызовов LLM-заглушки | `API-1`; `app/api.py:8-10` вызывает сервис без проверки длины |
```

Почему плохой: `API-1` — синхронная проверка `len(diff)` без общего состояния между запросами; результат каждого запроса не зависит от параллельности. Этот же кейс уже покрыт `tests_integration.md:8` с одним запросом — 20 параллельных запросов не добавляют новой информации.

## Запрос

Инструмент/модель: OpenCode CLI 1.18.30 / anthropic/claude-sonnet-5. Запрос выполнен отдельным тестовым запуском (без истории рабочего чата), инструменты записи запрещены (`OPENCODE_CONFIG_CONTENT='{"permission":{"*":"deny"}}'`).

Команда запуска:

```bash
OPENCODE_CONFIG=opencode.json OPENCODE_CONFIG_CONTENT='{"permission":{"*":"deny"}}' \
opencode run --agent plan --model vsellm/anthropic/claude-sonnet-5 \
  --file tests_load.md --file context.md --file tests_integration.md \
  --file tests_e2e.md --file TRAINING_PR.diff -- "<текст запроса>"
```

Текст запроса (сокращённо): дан явный критерий отбора нагрузочных сценариев (сценарий оправдан только если поведение системы зависит от конкуренции за общий ресурс/состояние, подтверждённое кодом в diff; иначе это integration-тест, повторённый N раз); дан «хороший» пример (`REL-1`) и «плохой» пример (`API-1`); задача — убрать/обосновать оба сценария на `API-1`.

Первая попытка запроса просила модель также предложить новый сценарий на `SEC-1` под конкурентной нагрузкой. Модель формально выполнила задачу (см. «Что получили»), но при последующей проверке (после эксперимента R.C.T.F., где тот же критерий был применён систематически ко всем правилам `context.md`) обоснование `SEC-1` признано недостаточным — см. «Что отклонили».

## Что получили

Модель (финальный прогон):

1. Убрала оба сценария на `API-1` («Отказ по длине без нагрузки на LLM», «Граница лимита diff») с обоснованием: `len(diff)` в `app/api.py:8-10` — чистая синхронная проверка, результат не зависит от соседних запросов; кейсы уже покрыты `tests_integration.md:8` и `tests_e2e.md` (сценарий «Граничный (лимит длины)») по одному запросу.
2. Обновила вводный абзац файла: сформулировала критерий отбора сценариев (нужен код в diff, подтверждающий общий ресурс).
3. Верно сослалась на `app/review_service.py:14` (сборка prompt f-строкой) при обосновании оставленного сценария `REL-1`.
4. Дополнительно (по первой версии запроса) предложила сценарий «Утечка секрета под конкуренцией (`SEC-1`)» с обоснованием через singleton `review_service` (`app/api.py:3`, `api.py:8-10`) — этот пункт впоследствии отклонён, см. «Что отклонили».

## Что изменили в исходном артефакте

- Файл и раздел: [`../../practice_01/tests_load.md`](../../practice_01/tests_load.md), вводный абзац и таблица «Сценарий» + раздел «Как использовали AI».
- Изменение: удалены 2 строки на `API-1` («Отказ по длине без нагрузки на LLM», «Граница лимита diff») как дублирующие `tests_integration.md`/`tests_e2e.md`; вводный абзац дополнен явным критерием отбора нагрузочных сценариев.
- Как проверили: проверил, что удалённые сценарии `API-1` действительно дословно совпадают по проверяемому условию с уже существующими строками `tests_integration.md:8` и `tests_e2e.md` (сценарий «Граничный (лимит длины)»); прогнал `make step1` — файл остаётся непустым и сохраняет требуемые ссылки.
- Что отклонили:
  - Версию строки `SEC-1` с ошибочной ссылкой `app/review_service.py:16` вместо `:14` — несогласована с остальными файлами Практики 1.
  - Идею формально «обосновать оставление» строк `API-1` вместо удаления — правило синхронное и не имеет состояния, разделяемого между запросами, обоснованной альтернативы удалению нет.
  - Сам сценарий `SEC-1` под конкуренцией — отклонён полностью после проверки в R.C.T.F. Обоснование: единственный факт, подтверждённый кодом (singleton `review_service`, `app/api.py:3`/`api.py:8-10`), доказывает лишь *возможность* архитектурной ошибки в ещё не написанном редакторе секретов, а не сам риск. В отличие от `REL-1` (риск — общее свойство любой синхронной блокирующей реализации, уже существует в diff), риск `SEC-1` под конкуренцией зависит от того, как будет реализован ещё не написанный код — то есть не подтверждён строкой diff, что нарушает `QA-1`. Применён тот же критерий, что и при отказе модели добавлять сценарий на `OBS-1` в эксперименте R.C.T.F.
