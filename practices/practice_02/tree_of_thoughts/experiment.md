# Tree of Thoughts

Файл ведёт OpenCode по вашим запросам. Агент записывает фактические результаты экспериментов и вносит изменения в связанные файлы. Свою оценку сообщайте ему в чате; вручную заполнять шаблон не нужно.

- Решение, для которого нужны альтернативы: как обосновать число параллельных запросов в нагрузочных сценариях [`../../practice_01/tests_load.md`](../../practice_01/tests_load.md), если Chain of Verification (см. [`../chain_of_verification/experiment.md`](../chain_of_verification/experiment.md)) показал, что ни `context.md`, ни `TRAINING_PR.diff` не задают требуемую конкурентность. Осложняющий факт: `product_management.md` и `adr.md` описывают сервис как работающий «с одним diff за раз».
- Критерии выбора: (1) соответствие коду `TRAINING_PR.diff` (не тестировать поведение, которого система по документированному решению не должна демонстрировать); (2) число новых недоказанных допущений сверх Context Pack (`QA-1`); (3) согласованность с уже принятым в файле принципом честного разделения источников (см. `few_shot`/`chain_of_verification`).

## Запрос

Инструмент/модель: OpenCode CLI 1.18.30 / anthropic/claude-sonnet-5, отдельный тестовый запуск (инструменты записи запрещены), файлы на вход: `tests_load.md`, `context.md`, `product_management.md`, `adr.md`, `TRAINING_PR.diff`.

Задача: рассмотреть минимум 3 разных подхода к обоснованию числа параллельных запросов — (A) буквально трактовать «один diff за раз» как запрет параллельности на уровне сервиса; (B) вывести число из предполагаемого размера команды ревьюеров; (C) признать отсутствие источника, зафиксировать открытый вопрос и взять минимальное число, доказывающее сам факт конкуренции за shared-ресурс. Для каждого — как меняется таблица, плюсы/минусы, какие новые недоказанные допущения (карго-груз) он вносит. В конце — выбор с обоснованием по конкретным ссылкам на файлы Практики 1.

## Варианты решения

| Альтернатива | Плюсы | Минусы | Оценка по критериям |
|---|---|---|---|
| A. Запрет параллельности (буквальная трактовка «один diff за раз») | Убирает саму необходимость выдумывать число; следует букве `product_management.md:12`/`adr.md:32` | Противоречит коду: `TRAINING_PR.diff` — обычный FastAPI-роут без lock/семафора, `ReviewService` не содержит логики сериализации; adr.md не описывает такое решение | Не проходит критерий 1 (противоречит коду) и косвенно критерий 2 (новое недоказанное требование — что сервис должен физически отвергать конкурентные HTTP-запросы) |
| B. Число из размера команды ревьюеров | Даёт наглядное бизнес-обоснование конкретных чисел | Ни один файл Практики 1 не называет размер команды — три независимых новых допущения (команда существует как единица, её размер, синхронность запросов); маскирует выдумку под «бизнес-факт» | Не проходит критерий 2 (больше недоказанных допущений, чем в текущей версии) и критерий 3 (менее честно, чем уже принятый в файле подход) |
| C. Минимальное число + открытый вопрос | Не добавляет число пользователей, которого нет в источниках; использует 2 как минимальный профиль для проверки возможной конкуренции. Это продолжает разделение источников из `few_shot`/`chain_of_verification` и согласуется с `tests_load.md:10` | `app/api.py:3` не доказывает singleton без определения из `app/dependencies.py`; число 2 не является доказанной нагрузкой и может быть недостаточно для редких состояний гонки | Проходит критерии как явно ограниченный инженерный выбор, но не как доказанное требование |

## Выбор

- Выбранная альтернатива: C — 2 параллельных запроса как минимальный воспроизводимый профиль проверки возможной конкуренции, плюс открытый вопрос в `context.md`.
- Почему: вариант A требует сериализации, которой нет в `adr.md` и `TRAINING_PR.diff`. Вариант B добавляет недоказанные допущения о команде ревьюеров. Вариант C не выдаёт `app/api.py:3` за доказательство singleton и явно отделяет инженерный выбор от требования источников.
- Как проверим: число «2» в `tests_load.md:7` помечено как инженерный минимум, а не оценка нагрузки; ограничение по источнику добавлено в `context.md:57`; `make step1` проходит.
