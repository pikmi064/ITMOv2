# Правила работы с «После пары»

Рабочая папка — `practices/practice_04/project`; документация сдачи также находится в `practices/practice_04`. Файлы практики 3 изменять нельзя. Пользователь подтвердил окончание работы другого агента и разрешил сдачу: ветка `practice_04` создана от `practice_03` без worktree. В commit включай только `practices/practice_04`; соседние незакоммиченные изменения не включай. PR открывай внутри форка `pikmi064/ITMOv2` с базой `practice_03`.

## Проект

- `server.py`: HTTP API на стандартной библиотеке Python, SQLite.
- `index.html`: HTML/CSS/JavaScript без сборки и внешних библиотек.
- `deadlines.py`: запрос сроков; `mcp_server.py`: MCP на официальном Python SDK.
- Данные пользователя: `data/tasks.sqlite3`. Не удаляй базу, не добавляй в Git, не заполняй её демонстрационными задачами без явной просьбы.
- Запуск: `python3 server.py`. Проверка: `python3 scripts/check.py`.

## Работа с инструментами

1. Для проверки пользовательского сценария загрузи skill `playwright`. Wrapper лежит в `.agents/skills/playwright/scripts/playwright_cli.sh` (проектная установка). Используй отдельную сессию `--session=practice4`. Сначала получи snapshot, затем действуй по ссылкам элементов. Артефакты сохраняй в `output/playwright/`.
2. Перед использованием незнакомого API библиотеки загрузи `context7-mcp`. Через MCP `context7` сначала найди библиотеку, затем запроси документацию с конкретным вопросом и версией. Не отправляй в запросы пользовательские задачи, ключи или содержимое базы.
3. На вопросы о реальных сроках вызывай `study_tracker_get_deadlines`. Не выдумывай задачи. Интервал включает сегодня и дату через `days` дней, просроченные задачи возвращаются отдельно.
4. После `write`, `edit` и `apply_patch` hook автоматически запускает runner и добавляет результат в ответ инструмента. При FAIL исправь ошибку и повтори проверку. Правки через shell и другие редакторы требуют ручного запуска runner.
5. Проверки используют временную SQLite, а не пользовательские данные. MCP открывает рабочую базу только для чтения.

## Подтверждения

Сохраняй фактические результаты в `output/`. Различай запуск через MCP-клиент, проверку обработчика hook и работу модели в OpenCode. Не выдавай один способ за другой. Мнение студента записывай только из диалога.

Для каждой новой проверки сохрани команду или вход, ожидаемый результат, фактический вывод и статус. Добавь запись со ссылкой на исходное доказательство в `EVIDENCE.md`; существенные результаты отрази в README. Ошибки и незавершённые запуски тоже сохраняй и помечай явно. Скриншот дополняет проверку поведения, но не заменяет вывод команды или MCP-вызова.
