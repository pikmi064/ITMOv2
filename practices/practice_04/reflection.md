# Рефлексия по практике 4

Рефлексия основана на нашем обсуждении и сохранённых результатах работы.

В начале обсуждения было непонятно, кто вызывает hook. Разобрали механизм: OpenCode запускает обработчик после выполнения инструмента, обработчик запускает runner и добавляет результат проверки в ответ модели. Пользователь предложил использовать hook для автотестирования, а для веб-проверок установить готовый skill.

Отдельно обсуждали назначение MCP: пользователь заметил, что `get_deadlines` предоставляет агенту функции продукта, а не инструменты для разработки. Сверились с заданием: оно требует полезный собственный tool, поэтому такой вариант подходит. Пользователь согласовал tool, Playwright и попросил Context7 для документации.

Технические наблюдения по выполненным проверкам:

- Playwright позволил проверить полный сценарий через браузер; статус задачи сохранился после перезагрузки.
- Собственный MCP возвращает только невыполненные задачи со сроками и отклоняет отрицательное число дней и строку вместо числа. Демонстрационные данные находятся во временной базе.
- Hook вернул PASS на исправном проекте и FAIL после внесения синтаксической ошибки во временную копию. Ошибка не затронула рабочее приложение.
- Context7 вернул реальные документы, однако примеры из основной ветки SDK уже используют новый API. Версия документации требует проверки даже при работающем MCP.
- Попытка запуска OpenCode с бесплатной облачной моделью получила HTTP 403 от провайдера. Эта ошибка сохранена отдельно от успешных проверок инструментов.
- Локальная модель прочитала правила, загрузила оба skill и вызвала MCP на правильном и ошибочном входе, но не завершила длинный сценарий за 180 секунд. Пользователь остановил это направление и уточнил, что практика 4 не требует локальной модели или агента из практики 3.
- После перехода на разрешённый пользователем Sonnet 5.5 проверка hook прошла целиком: модель изменила README через `edit`, OpenCode автоматически запустил runner и вернул `[AUTO CHECK PASS]`; модель подтвердила семь успешных тестов. Финальная сессия завершилась с кодом 0.
- Слишком короткий лимит шагов в первом облачном запуске помешал заключительному ответу, хотя правка и hook уже прошли. После увеличения лимита с трёх до шести шагов этот сценарий завершился успешно. Все прежние ошибки сохранены отдельно.

Небольшой проект помог показать пользу каждого подключения на конкретном действии. Playwright проверял форму и сохранение статуса, MCP возвращал данные SQLite, Context7 находил документацию, а hook выполнял быстрые проверки после правки. Проверка самого обработчика оказалась недостаточной для сдачи: потребовалось увидеть автоматический запуск в настоящей сессии OpenCode и результат в ответе модели.

Вмешательство пользователя потребовалось и в организации работы: он запретил менять файлы практики 3, отказался от worktree, потребовал оформлять каждую проверку как доказательство и указал ответвить `practice_04` от `practice_03`. Ветка создана после подтверждения, что другой агент закончил. В сдачу входят только файлы практики 4. По просьбе пользователя после завершения изменений отдельный субагент проверяет работу по всем пунктам задания.

Вывод из работы: статус `connected` подтверждает подключение, но не применение инструмента. Для сдачи нужны вход, фактический результат и связь этого результата с действием агента. Теперь они сведены в [реестр доказательств](project/EVIDENCE.md), а неудачные попытки отделены от итогового успешного запуска.

Подтверждения и текущий статус демонстрации: [project/DEMO.md](project/DEMO.md).
