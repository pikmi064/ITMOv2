## Что выбрано

Продолжен трекер учебных задач **«После пары»** из практики 4. Новая фича — кнопка **«Изменить»**: исправляет название, предмет и срок, сохраняя ту же задачу и отметку выполнения. Раньше для исправления пришлось бы удалять задачу и создавать заново.

Framework — **GitHub Spec Kit v1.2.4**. Это не библиотека приложения и не LLM-сервис: CLI устанавливает скрипты, шаблоны и инструкции для агента. Агент пишет требования/план/код. Приложение остаётся на Python/SQLite и HTML/JS без сборки и внешнего backend framework.

Два отдельных субагента выступали командами UI и логики. Они независимо подготовили draft, затем прочитали чужую спецификацию и общий контракт, выпустили согласованные версии. Все решения принял основной агент по твоему прямому поручению. Не нужно утверждать, что ты лично согласовывал каждый шаг или вручную писал код. Твоя задача на защите — понимать результат и демонстрировать поведение.

## Как запустить

Из корня репозитория:

```bash
cd practices/practice_05
make check
make spec-check
make demo
```

Открой **http://127.0.0.1:8050**. `make demo` создаёт пустую временную базу, удаляет её после завершения. Данные демонстрации не сохраняются между отдельными запусками — это намеренно. Для обычной работы `make serve` хранит задачи в `project/data/tasks.sqlite3`.

Для повторения браузерного прогона нужны Node 20+, Python 3.11+:

```bash
npm ci
npx playwright install chromium
make e2e
```

Если установлен Chrome: `PLAYWRIGHT_CHANNEL=chrome make e2e`. На этом компьютере агент использовал встроенный runtime с Playwright той же версии; в чистом окружении достаточно команд выше. Ошибка «Cannot find module playwright» означает, что ещё не выполнен `npm ci`. Ошибка отсутствия browser executable — не выполнен `npx playwright install chromium`.

## Демо на 3–5 минут

1. Покажи слайд 16 и карту критериев README: выбран другой framework, две спеки, одна фича.
2. Открой `specs/before/ui.md` и `logic.md`, затем контракт и итоговые спеки. Объясни три согласованных решения: отдельный PUT, полное тело трёх полей, особая обработка успешного сохранения с неуспешным обновлением списка.
3. Покажи `git show --stat ca88739`: там уже есть требования/план, но ещё **нет project/**. Затем покажи коммиты реализации. Это подтверждает, что спеки появились раньше кода, а не написаны задним числом.
4. В `make demo` создай «Подготовить ДЗ5», предмет «AI», срок. Отметь выполненной. Нажми «Изменить», поменяй все три поля, сохрани и обнови страницу. Статус выполнения сохранится.
5. Открой редактор, поменяй название и нажми Escape: данные прежние. Затем введи пробел вместо названия и сохрани: понятная ошибка, черновик на месте. Исправь и сохрани; при желании очисти предмет и срок.
6. Введи поиск, отредактируй название так, чтобы оно перестало совпадать: строка исчезнет из текущей выборки, поиск останется. Очисти поиск — задача появится.
7. Покажи `make check` и `evidence/browser-results.json`: там проверены перезапуск сервера, Unicode-границы, 404, сеть, клавиатура, мобильный экран и старые действия. Ошибки сети воспроизводятся автоматическим fault injection; вручную ломать сервер на защите не требуется.
8. Покажи `REVIEW.md`, сравнение фреймворков и рефлексию.

Без запуска можно открыть `evidence/demo-editor.png` и browser trace: `npx playwright show-trace evidence/browser-trace.zip`. Trace — запись реального теста с синтетическими данными, а не замена работающему демо.

## Как объяснить архитектуру

Нажатие «Изменить» заполняет native dialog текущими данными. Сохранение отправляет `PUT /api/tasks/{id}` с title/subject/deadline. Сервер сначала проверяет маршрут и поля, затем одним параметризованным UPDATE сохраняет три столбца; id/done не меняются. Ответ содержит актуальную запись с нормализованными пробелами. UI принимает её, закрывает редактор и перечитывает список для серверной сортировки.

Если PUT не удался, редактор остаётся с черновиком. Если PUT уже вернул 200, а следующий GET упал, нельзя утверждать «не сохранилось»: запись подтверждена, показывается отдельное предупреждение. Во время запроса повторное сохранение и закрытие заблокированы.

## Частые вопросы

**Где здесь SDD?** Требования — исходная точка реализации; две стороны согласовали контракт до кода, план/tasks связаны с критериями, тесты и независимое ревью сверяют поведение с ними. Одних Markdown файлов было бы недостаточно.

**Зачем PUT, если уже был PATCH?** PATCH оставили для done. PUT заменяет ровно редактируемую часть из трёх полей, поэтому нельзя случайно сбросить отметку выполнения. Неизвестные поля отвергаются.

**Что значит атомарно?** Сначала проверяются все поля; затем три значения меняются в одной транзакции. Неверный срок не позволяет частично сохранить название.

**Что не умеет?** Нет аккаунтов, истории, undo и защиты от одновременных правок: последнее сохранение побеждает. Идемпотентный повтор PUT не создаёт дубль, но способен перезаписать чужую новую правку — версий здесь нет.

**Почему данные не пропадают после перезапуска?** Они хранятся в SQLite; тест запускает новый процесс на той же временной БД и проверяет результат. `make demo` удаляет базу после всей демонстрации, поэтому новый отдельный demo-сеанс пустой.

**Какие ошибки нашли проверки?** Реальный Chrome переводил focus на BODY после полного Tab-обхода. Добавлено явное замыкание границ диалога и проверена блокировка клавиатуры при сохранении. Подробности в `evidence/focus-fix.md`; остальные замечания финального ревью перечислены в `REVIEW.md`.
