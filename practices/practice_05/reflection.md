# Рефлексия по практике 5

На этой практике я разобрался, как устроен Spec-Driven Development, и попробовал GitHub Spec Kit. Я научился разделять требования к результату, технический план и конкретные задачи реализации. Это помогло понять, что нужно согласовать до начала программирования и по каким условиям потом проверять работу.

Я научился формулировать спецификации: описывать цель изменения, действия пользователя, ограничения, ошибки и критерии приёмки. При подготовке двух отдельных спецификаций для UI и логики стало понятно, что каждая из них может выглядеть законченной, но при этом содержать разные предположения о поведении системы.

Поэтому важной частью работы было согласование. Я разобрался, как сравнивать две спецификации, находить расхождения и фиксировать принятые решения в общем контракте. После этого обе спецификации нужно обновить, чтобы в них совпадали данные, вызовы, ошибки и состояния. Теперь я лучше понимаю, зачем сохранять исходные версии: по ним видно, какие вопросы удалось решить до реализации.

В GitHub Spec Kit я познакомился с конституцией проекта, спецификацией, планом и списком задач. Научился ориентироваться в последовательности specify → clarify → plan → tasks → implement → converge. Разделение документов помогло сверить результат с требованиями: можно вернуться к отдельным условиям и проверить, что ничего не пропущено.

Для себя я вынес, что качество SDD зависит от конкретности требований и их согласованности. Наличие шаблонов само по себе не устраняет противоречия. Перед передачей задачи агенту нужно определить ожидаемое поведение и границы, а после реализации проверить результат по тем же условиям. В следующих работах хочу раньше уточнять спорные моменты и внимательнее проверять согласованность спецификаций, плана и задач.
