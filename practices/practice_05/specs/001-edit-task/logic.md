# Спецификация логики: редактирование задачи

Статус: согласована агентом команды логики с общим контрактом v1.0 до реализации. Независимый исходный вариант сохранён в `../before/logic.md`. Главный источник решений — `contracts/api.md`; команда UI исследована по `../before/ui.md`. Решения приняты агентами по поручению пользователя; ручная приёмка человеком не заявляется.

## User scenarios & testing

### US-L1 (P1): исправить задачу
Given задача существует, включая выполненную; When получен допустимый PUT; Then 200 содержит обновлённую задачу, GET и повторный запуск сервера возвращают те же title/subject/deadline, id и done прежние, другие записи не изменены.

### US-L2 (P1): очистить необязательные значения
Given предмет и срок заполнены; When переданы пустые subject/deadline; Then оба поля очищены. Повтор идентичного PUT даёт тот же результат без новой записи.

### US-L3 (P1): отказ без частичного изменения
Given задача существует; When тело не соответствует контракту; Then 400 с error, ни одно поле не изменено. Корректный повтор допустим. Допустимый запрос к отсутствующей задаче даёт 404 без создания.

### US-L4 (P1): сохранить существующие операции
Given добавлено редактирование; When клиент создаёт, получает список, отмечает выполненной/возвращает и удаляет задачу; Then прежние маршруты, форматы ответов и семантика сохраняются. GET продолжает использовать серверную сортировку.

## Functional requirements

- L-FR01: `PUT /api/tasks/{id}` принимает ровно три обязательных ключа `title`, `subject`, `deadline`, каждый строковый. Неизвестные ключи, включая id/done, отклоняются с 400. Частичного изменения PUT не выполняет; отсутствие ключа не означает очистку или сохранение старого значения.
- L-FR02: title после Python strip содержит 1–160 символов Python включительно; subject после strip — 0–80. Сохранять нормализованные строки. Пустая deadline очищает срок; иначе требуется действительная дата в каноническом `YYYY-MM-DD`. Пробелы у даты не нормализуются. Прошлые сроки допустимы.
- L-FR03: 200 возвращает полный объект `{id: integer, title: string, subject: string, deadline: string, done: 0|1}`. Сохранить id/done. UPDATE использует параметры и меняет только три редактируемых столбца. UPDATE и SELECT результата выполняются одной транзакцией. Валидация завершается до UPDATE, отказ не меняет БД.
- L-FR04: порядок проверки: маршрут/id → тело → наличие задачи. ID состоит из ASCII-цифр и обозначает число 1..9223372036854775807 включительно; ведущие нули разрешены. Другой маршрут, неверный id или выход за диапазон дают 404. Даже очень длинная строка цифр не вызывает server error.
- L-FR05: тело — UTF-8 JSON-объект размером 1..8192 байт и корректный Content-Length. Невалидный JSON/UTF-8, размер, длина, типы, отсутствующие/лишние поля дают управляемый 400. Корректный запрос к отсутствующей записи даёт 404; запись не создаётся. Ответы ошибки имеют JSON `{error: string}` и Content-Type `application/json; charset=utf-8`.
- L-FR06: существующий PATCH остаётся операцией done; PUT не расширяет его и не меняет формат `{ok: true}` старых действий. Таблица прежняя, миграции нет. Демонстрационные и автоматические проверки работают на отдельной временной БД.
- L-FR07: после 200 PUT клиент может считать запись сохранённой. Он заменяет локальную задачу полным ответом и отдельно делает GET ради серверного порядка. Неуспешный GET не отменяет успешную запись и не должен выдаваться за отказ PUT.
- L-FR08: повтор PUT идемпотентен по значениям; это позволяет повторить запрос при неизвестном результате из-за сети. Между клиентами действует последнее успешное сохранение, версий и конфликтов 409 нет. Даже идемпотентный повтор может перезаписать конкурентную правку — ограничение явно принято.

## Согласованные решения по интерфейсу

UI отправляет полный объект без id/done, использует пустые строки для очистки и не обрезает данные. Пока запрос выполняется, повторная отправка и закрытие заблокированы. При 400/404/сетевой ошибке draft остаётся доступен для исправления, повтора либо отмены. 404 не превращается в создание копии. При 200 диалог закрывается, локальные значения берутся из ответа; неудача GET сопровождается отдельным сообщением «Задача сохранена, но список не обновлён». Поиск/фильтр не сбрасываются; после изменения срока/названия задача может сменить позицию или исчезнуть из выборки.

## Success criteria и проверка

| Критерий | Доказательство |
|---|---|
| AC1: сохранены три поля и id/done после reload/рестарта | HTTP integration + сквозной UI сценарий |
| AC2: очистка, границы 160/80, отказы 161/81/дата/пробелы без записи | HTTP integration и граница формы |
| AC3: 400/404/сеть сохраняют draft, PUT success + GET fail различимы | UI E2E с контролируемыми отказами |
| AC4: старые создание/done/undone/удаление/поиск/фильтр/порядок | регрессия HTTP и UI |
| AC5: текст безопасен, клавиатура и 375 px | UI E2E и визуальная проверка |

Дополнительные HTTP проверки: done=0/1; високосная и невозможная дата; SQL/XSS-подобные строки; null/bool/array; unknown/missing keys; отсутствующий id, 0, Unicode-цифры, signed-int64 и очень длинный id; отсутствие частичной записи. Контракт не обещает защиту от нескольких клиентов, историю правок, аккаунты, синхронизацию или undo. Открытых вопросов, блокирующих генерацию кода в этих границах, нет.
