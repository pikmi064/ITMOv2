# UI specification: редактирование учебной задачи

Статус: независимый черновик команды UI, до согласования с логикой и до реализации.
Источник исследования: `practices/practice_04/project/index.html`; задание — слайд 16 `prenetation.pdf` (прочитаны все 16 слайдов).

## Пользовательская история и ценность

Студент исправляет название, предмет или срок существующей задачи, сохраняя её идентичность и статус выполнения. Не требуется удалять задачу и создавать её заново.

## Сценарии и условия приёмки

### US-UI-1 (P1): изменить существующую задачу

Given список задач загружен и задача видима, When пользователь нажимает «Изменить» у этой задачи, Then открывается редактор с текущими `title`, `subject`, `deadline`; фокус оказывается в названии. Идентификатор и статус выполнения не редактируются.

Given редактор открыт, When введены допустимые значения и нажато «Сохранить», Then отправляется ровно один запрос сохранения; повторная отправка заблокирована на время запроса; после успеха редактор закрывается и список показывает сохранённые данные.

Given изменена выполненная задача, When сохранение завершено, Then она остаётся выполненной с тем же id; статистика и доступные действия согласованы с актуальным списком.

### US-UI-2 (P1): отмена и восстановление после ошибки

Given редактор содержит несохранённые правки, When нажата «Отмена» или Escape, Then редактор закрывается без запроса изменения; список и хранилище сохраняют исходные значения. Закрытие возвращает фокус кнопке открытия, если она ещё существует.

Given введено пустое или пробельное название, When пользователь пытается сохранить, Then понятная ошибка сообщает ограничение; редактор остаётся открыт, черновик сохраняется. Поля имеют ограничения 160 символов названия и 80 символов предмета; дата необязательна.

Given сервер вернул ошибку или сеть недоступна, When запрос сохранения завершился неуспешно, Then редактор остаётся открыт, введённые значения сохраняются, ошибка видна и озвучивается; возможны повторное сохранение и отмена.

### US-UI-3 (P2): совместимость поиска и фильтров

Given установлен фильтр и поисковая строка, When пользователь сохраняет изменение, Then фильтр и строка не сбрасываются; список, порядок, счётчики и признак просрочки пересчитываются по сохранённым данным. Задача может исчезнуть из текущей выборки, если перестала соответствовать поиску или фильтру; это штатный результат.

Given список пуст или задачи скрыты фильтром, When отображается страница, Then существующие пустые состояния сохраняются, кнопка изменения доступна только у реально показанных задач.

## Функциональные требования

- UI-FR-01: у каждой видимой задачи есть отдельная кнопка «Изменить» с доступным именем, содержащим название задачи.
- UI-FR-02: одновременно открыт не более чем один редактор; он содержит подписанные поля названия, предмета, срока и кнопки «Сохранить»/«Отмена».
- UI-FR-03: доступны состояния closed → editing → saving → closed при успехе; editing/saving → error → editing при отказе. При сохранении поля и кнопки повторного действия блокируются; закрытие на время сохранения блокируется во избежание неопределённого результата.
- UI-FR-04: каждое поле и действие доступны с клавиатуры; если редактор модальный, Tab остаётся внутри него; сообщение ошибки связано с редактором и имеет `role=alert`.
- UI-FR-05: пользовательский текст выводится через текстовые DOM API, без интерпретации HTML; редактирование строки с `<script>` не исполняет код.
- UI-FR-06: интерфейс пригоден для узкого окна 375 px без горизонтальной прокрутки; кнопки и поля не перекрываются.
- UI-FR-07: создание, выполнение/возврат, удаление, поиск и фильтрация сохраняют прежнее назначение.

## Измеримый результат

Из существующей задачи пользователь меняет все три поля, сохраняет, перезагружает страницу и видит те же значения и прежний done/id. Отмена не меняет данные. Серверная ошибка не уничтожает черновик. В E2E проверяются эти сценарии, фильтры и хотя бы одна граница ввода.

## Предположения команды UI для согласования

1. Предлагается `PUT /api/tasks/{id}` с полным объектом `{title, subject, deadline}`; пустые предмет и срок передаются как `""`. Существующий PATCH с done остаётся отдельным действием.
2. Предполагается ответ 200 с актуальной задачей `{id,title,subject,deadline,done}`. UI затем обновляет список; отсутствие записи — 404 с JSON `{error: string}`, неверные поля — 400 в той же форме.
3. Предполагается нормализация пробелов сервером и неизменяемость done при редактировании.
4. После успешного сохранения UI перечитывает список, чтобы сохранить существующий серверный порядок.

## Открытые вопросы между командами

- Подтвердить метод PUT или выбрать совместимое расширение PATCH; зафиксировать одинаково в обеих спеках.
- Обязателен ли полный набор полей и должны ли неизвестные поля отвергаться? UI отправляет все три, без id/done.
- Если запись удалена другим клиентом, достаточно ли ошибки 404 с сохранённым черновиком и последующей отмены? Автоматическое создание копии не предлагается.
- Если сохранение прошло, но перечитывание списка не удалось, нужна явная разница между «не сохранено» и «сохранено, список не обновлён», чтобы не вводить пользователя в заблуждение.
- Конкурентное редактирование предполагается last-write-wins без версий; нужен явный общий договор.

## Границы

Не входят массовое редактирование, изменение done через редактор, аккаунты, облачная синхронизация, undo, история правок и предупреждение о конфликте версий. Существующие данные пользователя не используются для демонстраций; тесты работают на временной базе.
