# Исходная спецификация логики: редактирование задачи

Автор: отдельный агент «Команда логики». Статус: независимый draft до согласования с UI и до генерации кода. Источник задания: презентация практики 5, слайд 16. Исследованы существующий HTTP API и его тесты из практики 4. Фреймворк: GitHub Spec Kit, этап specify.

## Цель и границы

Студент исправляет название, предмет и срок уже созданной учебной задачи, сохраняя её идентичность и отметку выполнения. Используется существующая SQLite-таблица `tasks`; миграция не нужна. Не входят: история изменений, массовое редактирование, аккаунты, синхронизация, защита от одновременного редактирования из нескольких вкладок, изменение отметки выполнения через новую операцию.

## Пользовательские сценарии и приёмка

### US-L1 (P1): исправить существующую задачу

Given задача с `id=7`, `done=1` существует; When клиент сохраняет новые `title`, `subject`, `deadline`; Then API возвращает 200 и полную обновлённую задачу, повторный GET возвращает те же значения, `id=7` и `done=1` сохраняются. Изменена ровно одна строка, другие задачи не затронуты.

### US-L2 (P1): очистить необязательные поля

Given у задачи заполнены предмет и срок; When клиент передаёт `subject=""` и `deadline=""`; Then оба поля очищены, задача остаётся в списке и доступна после перезапуска сервера.

### US-L3 (P1): отклонить ошибку без частичного сохранения

Given исходная задача существует; When хотя бы одно новое поле неверно (включая невозможную дату); Then ответ 400 с JSON `{"error":"понятное объяснение"}`, ни одно поле не меняется. После исправления данных тот же запрос можно повторить.

### US-L4 (P1): предсказуемо обработать отсутствующую задачу

Given корректный положительный числовой id не существует; When поступает корректный запрос редактирования; Then ответ 404 с JSON error, новая запись не создаётся.

### US-L5 (P1): сохранить старые действия

Given новая операция добавлена; When выполняются существующие POST создания, GET списка, PATCH `{"done":true}` / `false`, DELETE; Then форматы ответов и семантика прежние, существующие тесты проходят.

## Предлагаемый API (требует согласования с UI)

`PUT /api/tasks/{id}` — полная замена только редактируемой части задачи. Тело:

```json
{"title":"Сдать ДЗ5","subject":"AI-инструменты","deadline":"2026-11-01"}
```

Успех 200:

```json
{"id":7,"title":"Сдать ДЗ5","subject":"AI-инструменты","deadline":"2026-11-01","done":1}
```

Предлагается отдельный PUT, чтобы не переопределять существующий PATCH отметки выполнения. Все три ключа обязательны даже для пустых необязательных значений. `id`, `done` и неизвестные поля отклоняются с 400; это предотвращает скрытое игнорирование опечаток и случайный сброс выполнения. MIME ответа: `application/json; charset=utf-8`.

## Функциональные требования

- L-FR01: `title` — строка, после strip от 1 до 160 символов включительно; `subject` — строка, после strip от 0 до 80. Сохранять нормализованные значения.
- L-FR02: `deadline` — пустая строка либо действительная календарная дата в точном каноническом формате `YYYY-MM-DD`. Принимать прошлые даты; это не ошибка предметной области. Пробелы вокруг непустой даты отклонять, как в существующем API создания.
- L-FR03: null, числа, bool, массивы вместо строк, тело не-объект, пропущенные и неизвестные поля дают 400. Некорректный JSON/UTF-8, пустое тело, некорректная длина и тело больше 8192 байт дают управляемую ошибку без записи.
- L-FR04: сначала разобрать маршрут и проверить допустимость id, затем тело, затем наличие задачи. Некорректный маршрут/id дают 404; корректный маршрут с неверным телом даёт 400 даже для отсутствующей задачи. ID — ASCII-цифры в диапазоне положительного SQLite signed int64. Отрицательные, дробные, Unicode-цифры и превышение int64 дают 404 без server error.
- L-FR05: вся валидация предшествует UPDATE. Один параметризованный UPDATE изменяет `title, subject, deadline`; `id, done` не входят в SET. Обновление и чтение результата — одна транзакция. Неизменённые значения также дают 200.
- L-FR06: пользовательские строки никогда не интерполируются в SQL. API не создаёт базу при ошибочном запросе; штатная инициализация остаётся при запуске сервера.
- L-FR07: GET продолжает сортировать по существующему правилу; изменение срока может изменить позицию задачи. UI должен заново получить список либо воспроизвести то же правило.

## Предположения и вопросы для согласования

1. UI должен выбрать между предложенным PUT полного редактируемого объекта и расширением PATCH. Предпочтение логики — PUT ради однозначной совместимости старого PATCH.
2. Что делать при потере сети после UPDATE, но до получения ответа? Предложение: сохранить draft и разрешить повторный PUT; операция идемпотентна по значениям. GET после успеха покажет фактическое состояние.
3. Где считать успешным сохранение: после 200 PUT или также после успешного GET? Предложение: PUT подтверждает запись; ошибка обновления списка показывается отдельно и не объявляет запись несостоявшейся.
4. UI должна явно передавать пустые строки для очистки. Нужно проверить согласованность формы с обязательностью трёх ключей.
5. Конкурентное редактирование: последнее успешное сохранение побеждает; версий и HTTP 409 пока нет. Это ограничение следует назвать при защите.

## План независимой проверки

Интеграционные HTTP тесты с временной SQLite: существующий done=0 и done=1; очистка; максимальные длины 160/80 и 161/81; високосная/невозможная дата; прошлый срок; XSS/SQL-подобные строки; отсутствие ключа и лишний ключ; int64 boundary и длинный id; отсутствующая задача; неизменность БД после каждого отказа; регрессия старого PATCH/POST/DELETE. Проверить, что UI и HTTP используют одинаковые данные и фактический ответ; отчёт автора сам по себе проверкой не считается.
