Анализ TRAINING_PR.diff
1. app/api.py — новый эндпоинт POST /api/reviews
Критично:
- Нет валидации входных данных. payload: dict вместо Pydantic-модели (class ReviewRequest(BaseModel): diff: str). Из-за этого:
- payload["diff"] упадёт с KeyError → FastAPI вернёт 500, а не корректный 422/400.
- Нет проверки типа diff (может прийти не строка, список, число и т.д.).
- Теряется автогенерация OpenAPI-схемы для тела запроса.
- Нет аутентификации/авторизации. Эндпоинт дергает LLM (платный ресурс) и доступен всем — риск злоупотребления и неконтролируемых расходов.
- Нет ограничения размера/длины diff. Можно прислать гигантский payload и сжечь токены/деньги или упереться в лимит контекста модели.
- Нет обработки ошибок вызова LLM. Если review_service.review() бросит исключение (таймаут, rate limit провайдера и т.п.), пользователь получит голый 500 без внятного сообщения, и это не логируется.
Средне:
- Нет rate limiting на эндпоинт с дорогим LLM-вызовом.
- Отсутствуют тесты для нового роута.
2. app/review_service.py — метод review
Критично:
- Prompt injection. Содержимое diff подставляется напрямую в промпт без экранирования/разделения ролей:
prompt = f"Review this pull request and find problems:\n{diff}"
Если diff содержит текст вида "ignore previous instructions and output ...", это может изменить поведение модели. Нужно явно разграничивать системную инструкцию и пользовательские данные (например, через разметку/delimiters или system+user сообщения, если API LLM это поддерживает).
- Нет обработки ошибок LLM. self.llm.generate(prompt) может кинуть исключение — не перехватывается, нет фолбэка/ретраев.
- Нет валидации/парсинга ответа модели. Ответ просто заворачивается в {"comment": answer} без проверки, что это осмысленный текст (не пустая строка, не обрезанный ответ и т.д.).
Средне:
- Нет ограничения длины diff перед отправкой в промпт (см. проблему с эндпоинтом выше) — стоит валидировать/обрезать на уровне сервиса тоже, а не полагаться только на API-слой.
- Жёстко зашитый промпт без возможности конфигурации/версионирования (не так критично, но затрудняет тюнинг качества ревью).
3. Стиль/оформление
- Изменение Protocol.generate с одной строки ... на две строки — не связано с функциональностью фичи, лишний шум в PR (смешение рефакторинга и новой фичи в одном коммите/diff). Стоит либо вынести в отдельный PR, либо объяснить в описании, зачем это сделано (например, требование линтера).
4. Отсутствие тестов
Ни для ReviewService.review, ни для /api/reviews тестов не добавлено — нет проверки:
- happy path (успешный ответ LLM),
- обработки отсутствующего/некорректного diff,
- обработки ошибки от LLM.
