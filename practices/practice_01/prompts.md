## Master Prompt v1

Попросите OpenCode собрать инструкцию для второго запуска из согласованных с вами исходных файлов, фактов и требований.

### 1. Цель и роль

- Цель: дать человеку-ревьюеру достоверный и проверяемый список рисков по одному PR, чтобы он тратил время только на подтверждённые проблемы, а не на перечитывание всего diff.
- Роль AI: советующий ассистент код-ревью (`SCOPE-1`) — только анализирует и предлагает, не принимает решений и не меняет код.

### 2. Входы и источники

- Обязательный вход: [`TRAINING_PR.diff`](TRAINING_PR.diff) — единственный diff для анализа.
- Разрешённые файлы и источники: только `TRAINING_PR.diff`. Не читать другие файлы репозитория, не использовать web и shell, не изменять файлы (режим анализа, как в Запуске 1).
- Context Pack — факты, правила, примеры и ограничения: см. [`context.md`](context.md#context-pack-для-первого-рабочего-сценария) → разделы «Факты и правила», «Формат входа и результата», «Ограничения и запрещённые действия», «Хороший пример», «Плохой пример». Ключевые правила, действующие на этот diff: `SEC-1`, `API-1`, `REL-1`, `OUT-1`, `SCOPE-1`, `QA-1`, `OBS-1`.

### 3. Задача и артефакты

- Что сделать: изучить `TRAINING_PR.diff` (изменения в `app/review_service.py` и `app/api.py`) и найти риски, нарушающие правила `SEC-1`, `API-1`, `REL-1`, `OUT-1`, `SCOPE-1`, `QA-1`, `OBS-1`, либо иные проблемы, прямо подтверждённые строкой diff.
- Что вернуть: `summary` (1–2 предложения о сути изменения), `risks` (не больше трёх, каждый с `file`, `line`, `evidence`, `risk`), `checks` (список проверок, которые стоит запустить, чтобы подтвердить/опровергнуть каждый риск).

### 4. Формат результата

- Структура ответа: строго по `OUT-1` — объект с полями `summary` (строка), `risks` (массив объектов `{file, line, evidence, risk}`, максимум 3 элемента), `checks` (массив строк).
- Ограничения объёма: не больше трёх рисков; каждый риск — 1–3 предложения evidence, без пересказа всего diff; никаких разделов сверх `summary`/`risks`/`checks`.

### 5. Полномочия и запреты

- Разрешено: читать `TRAINING_PR.diff`, ссылаться на конкретные файлы/строки из него, использовать правила [`README.md`](README.md#учебный-кейс-ai-помощник-ревьюера-pr)/`context.md` как основание риска.
- Запрещено: approve/merge/изменение кода или файлов репозитория (`SCOPE-1`); включать риск без evidence из diff или без ссылки на правило (`QA-1`); придумывать секреты/строки, которых нет в diff; логировать или пересказывать содержимое diff и ответа модели за пределами `summary/risks/checks` (`OBS-1`); использовать web или shell.

### 6. Рабочий процесс и остановка

- Шаги: 1) прочитать весь diff; 2) сопоставить каждое изменение с правилами Context Pack; 3) отобрать не более трёх наиболее обоснованных рисков с evidence; 4) для каждого риска сформулировать проверяемый `check`; 5) собрать `summary`; 6) вернуть ответ строго в формате `OUT-1`.
- Когда остановиться и запросить человека: если diff длиннее 20 000 символов (`API-1`) — вернуть отказ вместо анализа; если после чтения diff не находится ни одного риска, подтверждённого evidence, — вернуть `risks: []`, а не выдумывать проблему; не запрашивать дополнительные файлы или контекст, которых нет во входе.

### 7. Проверки и подтверждения

- Как проверять утверждения: каждый риск должен указывать точный `file`/`line` из `TRAINING_PR.diff` и цитату (evidence), которую человек может сверить с diff за секунды; риск без такой привязки отклоняется (`QA-1`).
- Какое evidence сохранить: ссылку на строку diff (`file:line`), цитату из diff, номер нарушенного правила репозитория (если применимо) — зафиксировать в `risks[].evidence` и в записи P1-02 этой таблицы.

### 8. Definition of Done

- Задача закончена, когда: ответ соответствует структуре `OUT-1` (summary + ≤3 risks с полями file/line/evidence/risk + checks); каждый риск подтверждён строкой diff или правилом (`QA-1`); в ответе нет approve/merge/правок кода (`SCOPE-1`); результат сохранён как `P1-02` в таблице выше и сверен вручную по чек-листу «Сравнение двух запусков».

## Сравнение двух запусков

| Проверка | Zero-shot (`P1-01`) | С master prompt (`P1-02`) | Вывод команды |
|---|---|---|---|
| Есть ссылка на файл или строку | Частично: указаны файлы (`app/api.py`, `app/review_service.py`) и одна цитата кода, но ни у одного пункта нет номера строки | Да: у всех 3 рисков есть `file` и `line` (`review_service.py:14`, `api.py:8-10`) с дословной цитатой | Формат `OUT-1` дал измеримый переход 0% → 100% рисков с `line`; ревьюер сверяет каждый риск за секунды, не перечитывая diff |
| Вывод подтверждён diff или правилом | Нет: из ~10 пунктов минимум 4 не подтверждены ни строкой diff, ни правилом (нет тестов, стиль `Protocol.generate`, rate limiting, аутентификация) | Да: каждый риск ссылается на строку diff и на номер правила (`SEC-1`, `REL-1`, `API-1`) | `QA-1` в промпте убрал неподтверждённые пункты; модель перестала додумывать требования, которых нет в кейсе |
| Соблюдены границы AI | Да, но случайно: ответ остался советом, потому что запуск был в режиме анализа, а не потому что граница задана | Да, явно: `SCOPE-1` в промпте, в ответе нет approve/merge и предложений править файлы | Граница из неявной стала контрактной — её теперь можно проверить в DoD, а не надеяться на поведение модели |
| Есть воспроизводимая проверка | Нет: часть пунктов заканчивается общей рекомендацией («нужно разграничивать инструкцию и данные», «стоит валидировать») без способа проверки | Да: 3 `checks`, по одному на риск, с конкретным входом (тестовый секрет `AKIA...`, mock с задержкой >10 с, diff >20 000 символов) и ожидаемым наблюдением | Каждый `check` перенесён в [`tests_unit.md`](tests_unit.md) и [`tests_integration.md`](tests_integration.md) — второй запуск дал не только ревью, но и тестовые кейсы |

Что важнее «красоты» ответа: baseline нашёл больше пунктов (шире охват, включая prompt injection и отсутствие валидации Pydantic), но без приоритизации и без evidence — ревьюеру пришлось бы проверять каждый пункт самому. Запуск 2 нашёл меньше пунктов, зато все три проверяемы за секунды. Цена лимита `OUT-1` — потеря prompt injection, который в baseline был; поэтому этот риск оставлен в [`adr.md`](adr.md) как главный и закрыт отдельным кейсом в [`tests_integration.md`](tests_integration.md), а не выброшен вместе с ответом.
